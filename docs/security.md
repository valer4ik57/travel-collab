# Безопасность Travel-Collab

Документ фиксирует реализованные механизмы безопасности и ограничения локальной дипломной версии проекта.

## Реализованные механизмы

### Пароли

Пароли пользователей не должны храниться в открытом виде. При регистрации backend хеширует пароль с использованием bcrypt, а при входе сравнивает введённый пароль с сохранённым хешем.

### JWT-аутентификация

После успешного входа пользователь получает JWT. Токен передаётся в защищённые REST API через заголовок:

```text
Authorization: Bearer <token>
```

Если токен отсутствует или некорректен, backend отклоняет запрос.

### Проверка доступа к поездке

Доступ к данным поездки разрешается только её участникам. Перед операциями с маршрутами, точками, расходами, участниками и сообщениями backend проверяет наличие пользователя в составе `trip_members`.

### Роли участников

В поездке используются роли:

- `owner` — владелец поездки;
- `editor` — участник с правом редактирования;
- `viewer` — участник только для просмотра.

Frontend скрывает недоступные действия, но окончательная проверка должна выполняться на backend.

### WebSocket

WebSocket-подключение выполняется с JWT-токеном. Перед установкой соединения backend проверяет токен и принадлежность пользователя к поездке. Это не позволяет подключиться к комнате поездки без участия в ней.

### Секреты и окружение

Секреты и параметры запуска хранятся в `.env`, который не должен попадать в Git. В репозиторий добавляется только `.env.example` без реальных секретов.

### CORS

Backend поддерживает список допустимых frontend-адресов через `FRONTEND_URLS`. Это нужно для локального web-запуска, мобильного web-доступа и Capacitor-приложения.

## Ограничения локальной версии

Текущая версия является дипломным MVP и предназначена для локального запуска. Поэтому в ней есть ограничения:

- используется HTTP/WS, а не HTTPS/WSS;
- JWT хранится на клиентской стороне;
- refresh-токены не реализованы;
- rate limiting для защиты от перебора паролей не реализован;
- журналирование действий пользователей не реализовано;
- Android APK собирается как debug APK;
- CORS в локальной разработке может быть шире, чем в production.

## Что нужно добавить для production

Перед промышленным развёртыванием систему следует усилить:

1. Настроить HTTPS/WSS через reverse proxy, например Nginx или Caddy.
2. Ограничить CORS только реальными доменами frontend.
3. Заменить development `JWT_SECRET` на длинный случайный секрет.
4. Добавить refresh-token механизм и отзыв сессий.
5. Добавить rate limiting для входа и регистрации.
6. Добавить аудит действий: создание поездок, удаление точек, изменение расходов.
7. Настроить secure cookie или другую более защищённую стратегию хранения токенов.
8. Собрать release APK/AAB с подписью, если приложение нужно распространять вне локальной демонстрации.

## Формулировка для защиты

В рамках дипломной версии реализованы базовые механизмы безопасности: хеширование паролей, JWT-аутентификация, проверка принадлежности пользователя к поездке, разграничение ролей и проверка WebSocket-подключений. Для промышленной эксплуатации требуется дополнительное усиление: HTTPS/WSS, строгий CORS, rate limiting, refresh-токены и аудит действий.
