# Безопасность Travel-Collab

Документ фиксирует реализованные механизмы безопасности, production-доработки и ограничения проекта.

## Реализованные механизмы

### Пароли

Пароли пользователей не хранятся в открытом виде. При регистрации backend хеширует пароль с использованием bcrypt, а при входе сравнивает введённый пароль с сохранённым хешем.

### JWT-аутентификация

После успешного входа пользователь получает JWT. Токен передаётся в защищённые REST API через заголовок:

```text
Authorization: Bearer <token>
```

Если токен отсутствует или некорректен, backend отклоняет запрос.

### JWT не равен правам доступа

JWT подтверждает личность пользователя, но не даёт ему автоматический доступ ко всем данным. Для операций внутри поездки backend отдельно проверяет запись пользователя в `trip_members` и его роль в конкретном `trip_id`.

### Проверка доступа к поездке

Доступ к данным поездки разрешается только её активным участникам. Перед операциями с маршрутами, точками, расходами, участниками и сообщениями backend проверяет принадлежность пользователя к поездке.

### Роли участников

В поездке используются роли:

- `owner` — владелец поездки;
- `editor` — участник с правом редактирования;
- `viewer` — участник только для просмотра.

Frontend скрывает недоступные действия, но окончательная проверка выполняется на backend. Это защищает API от прямых запросов, которые обходят интерфейс.

### WebSocket

WebSocket-подключение выполняется с JWT-токеном. Перед установкой соединения backend проверяет токен и принадлежность пользователя к поездке. Дополнительно проверяется HTTP `Origin`: в production разрешаются только origin из `FRONTEND_URL` и `FRONTEND_URLS`.

Токен WebSocket пока передаётся через query-параметр, потому что браузерный `WebSocket` API не позволяет удобно добавить обычный `Authorization` header. Для дипломного публичного демо этот вариант усилен HTTPS/WSS и проверкой Origin. Более строгий production-вариант — короткоживущий одноразовый WS-token или secure httpOnly cookie.

### CORS

Backend поддерживает список допустимых frontend-адресов через `FRONTEND_URLS`.

- В `development` разрешаются явно заданные origin и локальные адреса для web/mobile-разработки.
- В `production` разрешаются только явно заданные `FRONTEND_URL` и `FRONTEND_URLS`; wildcard `*` запрещён.

### Rate limiting

На endpoint-ы регистрации и входа добавлен in-memory rate limiting. Он ограничивает частоту запросов по IP, HTTP-методу и пути. Это снижает риск примитивного перебора паролей и спама регистрациями.

### Ограничение размера запросов

Через `MAX_REQUEST_BODY_BYTES` ограничивается размер входящих HTTP-запросов. Это защищает backend от слишком больших JSON-body в публичном режиме.

### Секреты и окружение

Секреты и параметры запуска хранятся в `.env`/`.env.production` и не должны попадать в Git. В репозиторий добавляются только примеры `.env.example` и `.env.production.example` без реальных секретов.

В `production` backend не стартует, если `JWT_SECRET` короткий или похож на шаблонное/dev-значение.

## Ограничения текущей версии

Проект подготовлен для публичной дипломной демонстрации, но не является полноценной промышленной платформой. Ограничения:

- refresh-токены не реализованы;
- JWT хранится на клиентской стороне;
- аудит действий пользователей не реализован;
- rate limiting является in-memory и сбрасывается при перезапуске backend;
- одноразовый WebSocket-token не реализован;
- Android APK собирается как debug APK;
- нет сложного мониторинга и alerting.

## Что можно добавить дальше

1. Refresh-token механизм и отзыв сессий.
2. Secure httpOnly cookie или одноразовые WS-token для WebSocket.
3. Персистентный rate limiting через Redis/PostgreSQL.
4. Audit log действий пользователей.
5. Release APK/AAB с подписью.
6. Централизованный мониторинг и алерты.

## Формулировка для защиты

В рамках проекта реализованы базовые механизмы безопасности: bcrypt для паролей, JWT-аутентификация, server-side проверка принадлежности пользователя к поездке, роли `owner/editor/viewer`, проверка WebSocket-подключения, строгий CORS/Origin для публичного режима, запрет слабого JWT-secret в production и rate limiting на вход и регистрацию. При этом я разделяю учебно-демонстрационный публичный запуск и полноценную промышленную эксплуатацию: для промышленного режима дополнительно потребовались бы refresh-токены, аудит действий, одноразовые WS-token и расширенный мониторинг.
